## How to use this file

1. Read **Invariants** — they are the things a fix must not break, and two of them are
   counter-intuitive enough that a cold session will get them wrong without reading.
2. Find the first unticked row in the **Ledger**. Rows are ordered by wave; do not start a
   wave before its predecessor is ticked, and do not start a row whose `Depends on` is unticked.
3. Each row is **self-contained**: files, the change, the acceptance test, and the sessions that
   evidence it. You should not need to re-derive anything from the transcripts to execute a row.
4. Follow the **Verification protocol**. A row is not tickable until its acceptance test passes.
5. Append to `SESSION_LOG.md` before you finish. The *Surprises* line is the one that matters.
6. If reality diverges from the plan, follow the **Re-planning protocol** — amend this file in
   the same commit as the work, do not leave the plan stale.
7. **When the user asks** (normally at the end of a session), update the **summary table**
   — the one-line-per-fix tracker shared with Thomas, at <https://claude.ai/artifact/JtrwLwRZnRihfe8kHj3EaJ>. Edit the `ROWS`
   array in `docs/prepilot-fixes/summary-table.html`, then republish that file with the
   Artifact tool, passing the URL above as `url` so the link stays the same. **Every row carries a `sev` (P1/P2/P3, defined on the page: P1 = the lawyer gets something wrong or misleading and cannot tell, or hits a dead end; P2 = correct but incomplete or harder to check; P3 = presentation, unseen wording or tooling).** It grades the defect, not the fix, so it does not change when a row is fixed. The table sorts itself by status then severity, so add rows anywhere in `ROWS`; plan order is the tie-break. (Added 2026-09-23 at the user's request.)

## Invariants

These hold for every row. Breaking one is a worse outcome than leaving a bucket unfixed.

1. **Honest failure is the most-praised behaviour in the corpus and must survive every fix.**
   Three lawyers praised it unprompted, two of them at 5/5 confidence; CambeulW gave 5/5 in
   session 6374 *because* AILA said it could not find something. Every fix to B3 and B5 must
   make the negatives **true** — it must not make the tool more willing to guess. A fix that
   raises the answer rate by lowering the evidence bar is a regression even if the ledger row
   goes green.

2. **Code enforcement beats prompt obedience.** This is already the house style (Phase-2 nudges,
   the parliamentary search budget, the `local_prompt_cache` drafting override). Where a row
   offers a choice between "tell the model to" and "make it so", take the second. B3(b), B7 and
   B12's disclosure footer are all specified this way deliberately.

3. **Do not change retrieval and measure in the same step.** Wave 1 fixes the input to every
   other measurement — while `_matches_jurisdiction` returns `False` for every real extent
   value, no retrieval-quality number means anything. Baseline first (Wave 0), then Wave 1,
   then re-baseline before Wave 3.

4. **A single replay pass is not evidence.** The model is stochastic. Acceptance for any row
   whose test involves an LLM is **n=3, all three clean** for a session classified FAIL, and
   **n=1** for one classified DEFECT (see *Replay configuration* — DEFECT symptoms are mostly
   deterministic, and an ambiguous one gets promoted to n=3). Rows marked *deterministic* have no
   model in the loop at all and need n=1 regardless.

5. **Additive and fail-soft, as everywhere else in this codebase.** No row here justifies a
   breaking change to a stored shape. New columns default; new fields are optional; a failure
   in a diagnostic must never fail the research run.

6. **The lawyers' own words are the ground truth, not the feedback scores.** Two sessions
   (6376, 6361) carry `Q7a = yes` with free text saying the opposite. Where a row cites a
   session, read the transcript, not the score.

## Verification protocol

Every row states its own acceptance test. Three kinds, and the distinction matters:

| Kind | What it means | n | Where it lives |
|---|---|---|---|
| **Deterministic** | No LLM. A unit test, or a static check over stored output. | 1 | `server_py/tests/` |
| **Replay** | Re-run the original session's question(s) through `/api/system/chat` and assert on the `audit` trace + answer. | 3 | `evidence/replay/` (gitignored output) |
| **External** | Answer comes from a third party, not from code. | — | `SESSION_LOG.md` |

### Iterate on a seam before you pay for a replay (Session 17, 2026-09-21)

**`python -m tools.seam_replay` is the cheap step before an acceptance sweep,
not a replacement for one.** Every fix since P2.2 has been a prompt or
composition change, and P3.1 established that retrieval upstream of them was
already correct — yet the iterate loop was a whole session replay. The tool
rebuilds ONE seam's input from a stored run file, using the product's own
builders, and makes the single model call:

```
python -m tools.seam_replay synthesis --run <run.json> --turn 1 [--without-fix]
python -m tools.seam_replay worker    --run <run.json> --turn 1 [--delegation K]
python -m tools.seam_replay <seam> --run … --dry-run     # payload only, no call
```

Measured on the fixtures it was built against: the **Worker composition** seam
costs **$0.03** a draw against $0.55 for a 6348 replay, and the **Deep Research
synthesis** seam **$0.11** against $0.61-0.79 for the turn. It needs no server.
`--without-fix` rebuilds the seam at an older revision (prompt constant read
from git, pinpoint block stripped), which is what makes an A/B possible.

**What it cannot do:** everything upstream is frozen — the retrieval is
whatever the recorded run retrieved — so it cannot test a retrieval change and
it cannot produce an acceptance. Use it to find the shape of a fix, then spend
on the n=3 replay once. **On a HALTED delegation the Worker seam closes with the
product's own write-up instruction (P3.8, Session 18), so a draw there IS the
write-up round the product makes at the step cap** — that is how P3.8's design
was settled for $0.21 before any code, and how its round is evidenced on
fixtures where a live replay may not halt at all. **`--from-raw` (P3.11,
Session 19) rebuilds each summarised result's appended blocks from its
recorded `raw_result` through `agent_shared.summarised_result_blocks`, the
product's own builder** — the seam replays `final_result`, so a block the
product builds from the raw result (P1.6's URLs, P3.11's outline) reaches it
only this way; the recorded payload is the before-column and `--from-raw`
the after. The pinned configuration runs at temperature 0, so one payload
gives one sample: count draws per payload, not draws. And the seam is an
approximation the other way too: P3.11's one live miss DELIVERED when its
own recorded payload was replayed here — a seam pass is not a live pass.

**Where the money goes, measured over `wave2`** (41 sessions, $29.55), for
scoping any future sweep: Deep Research turns are **20 of 155 turns and 48% of
the spend** ($0.71 each); 14 turns carry 45%; 8 sessions carry 53%; the
cheapest half of all turns costs $4.16 together. Other levers, none yet built:
replay only up to the graded turn, exclude Deep Research sessions from a row
that cannot touch them, reuse run files when `git diff <rev> HEAD --
server_py/src` is empty (done by hand twice in Session 16), and a cheap model
for plumbing smokes only — **never** for a graded run, where the pinned model
is the one the pre-pilot ran on.

## Re-planning protocol

This plan is expected to change. Two rules:

- **Amend the plan in the same commit as the work that invalidated it.** A session that
  discovers a row is wrong edits the row, adds a `~~strikethrough~~` note saying what was
  believed and what is now known, and says so in `SESSION_LOG.md`. A stale plan is the specific
  failure mode this structure exists to prevent.
- **New findings become new rows, not scope creep inside an existing row.** If executing P1.1
  uncovers a second defect, add P1.5 rather than widening P1.1 — otherwise the ledger stops
  reflecting what was actually verified.

Wave 5 rows are **external** and have unknown lead times. Open them early and in parallel;
they are not blockers for anything in Waves 0–4.
